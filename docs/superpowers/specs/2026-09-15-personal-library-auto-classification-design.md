# LocalRAG 个人总库自动编目设计

> 日期：2026-09-15
> 状态：已完成交互设计确认，等待书面审阅
> 范围：个人总库、LLM 自动分类、标签与摘要、分类侧栏、故障兜底

## 1. 背景

LocalRAG 已支持多格式文档解析、分块、向量化、知识库、标签、混合检索和带引用问答，但大量跨领域个人文档仍依赖用户手工建立知识库或维护标签。文档数量增长后，逐份整理不可持续。

本设计将默认使用用户已经配置的 OpenAI 兼容 LLM，为每份完成解析的文档执行一次自动编目。系统生成稳定的顶层分类、受控的二级分类、多个标签和简短摘要；用户不需要逐份确认或修正。现有本地 Embedding 仅作为 LLM 不可用时的兜底，不新增本地生成式大模型。

## 2. 目标与非目标

### 2.1 目标

- 默认提供一个可跨领域检索的“个人总库”。
- 文档解析完成后自动生成主分类、二级分类、3～8 个标签和摘要。
- 顶层分类稳定，二级分类可以由 LLM 自动创建，但必须去重、可审计、可撤销。
- 分类用于整理和筛选，不在默认情况下缩窄聊天检索范围。
- LLM 故障不得阻塞文档入库、向量化、搜索或问答。
- 不上传原文件、完整正文、本地路径或向量索引；只发送脱敏后的代表片段。
- 所有分类数据与操作严格按用户隔离。

### 2.2 非目标

- 第一版不实现 GraphRAG、无监督聚类或知识图谱。
- 第一版不自动修改顶层分类。
- 第一版不建设企业连接器、RBAC 或源权限同步。
- 第一版不以分类替代现有知识库数据结构，也不删除现有多知识库能力。
- 第一版不要求用户处理“待分类”队列，也不把人工修正作为正常流程。
- 第一版不向云端发送整份文档，即使文档长度小于模型上下文窗口。

## 3. 已选方案与备选方案

### 3.1 已选：LLM 自动编目为主

本地完成解析、脱敏和代表片段采样后，调用现有 LLM 一次，返回结构化编目结果。该方案对复杂、跨领域文档的理解最好，不占用额外本地推理资源，也符合用户已经接入 LLM 的现实使用方式。

### 3.2 故障备选：Embedding 匹配已有分类

当 LLM 未配置、超时、限流或连续返回无效结果时，复用 `bge-small-zh-v1.5` 的文档向量，与现有分类描述向量计算相似度。它只匹配已有分类，不创建新分类或生成摘要。无法可靠匹配时归入“其他”。

### 3.3 后续备选：LLM 深度编目

后续可提供用户主动触发的深度编目模式，对疑难文档使用更多代表片段或分段汇总。它不属于第一版默认路径，避免多次调用带来的成本与延迟。

## 4. 信息架构

### 4.1 个人总库

保留 `KnowledgeBase` 及 `Document.kb_id`，兼容现有数据和未来隔离需求。产品默认入口改为“个人总库”视图，它聚合当前用户有权访问的全部文档。新导入默认进入用户的默认知识库；已有知识库不做破坏性迁移。

分类是用户级虚拟目录，不对应独立向量集合。聊天默认检索当前用户的全部可用文档，避免跨类别问题漏召回。

### 4.2 分类层级

第一版最多两级：固定顶层分类和自动生成的二级分类。

默认顶层分类：

1. 工作与项目
2. 技术与工具
3. 学习与研究
4. 财务与法律
5. 健康与生活
6. 兴趣与收藏
7. 其他

系统不得自动新增、重命名、合并或删除顶层分类。LLM 可以在前六个顶层分类下创建二级分类；无法稳定判断时使用“其他”。

### 4.3 标签

每份文档只有一个最终分类路径，但可以有多个标签。分类表达稳定的主题归属，标签表达人物、项目、地点、技术、年份、文档用途等交叉维度。

复用现有 `Tag` 和 `DocumentTag`，但迁移必须把标签唯一性从全局 `name` 调整为用户级规范化名称，避免不同用户之间共享或冲突。自动标签和用户标签都保留来源，自动重新编目不得删除用户手动添加的标签。

## 5. 数据模型

### 5.1 `categories`

- `id`
- `user_id`，非空并关联 `users.id`
- `parent_id`，顶层为空，二级分类关联同一用户的顶层分类
- `name`
- `normalized_name`，用于同义名称去重
- `path_key`，由规范化后的完整分类路径生成
- `description`，同时作为 LLM 上下文和 Embedding 兜底原型
- `is_system`，标记固定顶层分类
- `is_archived`，可逆合并时归档旧分类
- `created_by`：`system | llm | user`
- `created_at`、`updated_at`

约束：`(user_id, path_key)` 唯一，避免 MySQL 中可空 `parent_id` 绕过唯一性；服务层强制最大深度为二级；父子分类必须属于同一用户。

### 5.2 文档编目字段

`documents` 增加：

- `category_id`，可空外键
- `classification_status`：`pending | running | completed | fallback | failed`
- `classification_method`：`llm | embedding | none`
- `classification_confidence`
- `classification_version`
- `classification_error`，只保存脱敏错误摘要
- `classified_at`
- `auto_summary`

文档解析状态与编目状态相互独立。`Document.status=completed` 表示文档可检索，不要求编目成功。

`document_tags` 增加 `source`（`llm | user`）、可空 `confidence` 和可空 `classification_event_id`。自动重新编目只替换 `source=llm` 的关联，不删除 `source=user` 的标签。

### 5.3 `classification_events`

记录自动创建分类、分类迁移、标签变更、分类合并和撤销：

- 用户、文档、操作类型和时间
- 变更前后的分类与自动标签快照
- 文档版本、分类器版本、Prompt 版本和模型名称
- 调用方法、置信度和故障原因
- `reverted_at` 与关联的反向事件

事件只保存结果和必要审计信息，不保存发送给 LLM 的文档片段。

## 6. 自动编目流水线

```text
上传/URL 导入
  → 现有解析与分块
  → 现有 Embedding 与索引
  → 文档进入可检索状态
  → 异步自动编目任务
      → 构造脱敏分类包
      → 调用结构化 LLM 分类器
      → 校验与分类去重
      → 保存分类、自动标签、摘要和审计事件
      → 通知前端刷新分类计数
```

### 6.1 分类包

分类包默认不超过 12,000 个 Unicode 字符，包含：

- 文件显示名和扩展名，不包含本地绝对路径或存储文件名；
- 文档标题、章节标题和表格标题；
- 从开头、中间、结尾及语义代表块采样的文本；
- 经过本地敏感信息过滤的片段；
- 当前分类树的名称和说明；
- 当前用户常用标签的受限列表。

分类包构造器先去除密钥、令牌、数据库连接串、证件号、手机号、邮箱等明确敏感模式，再按内容位置和语义代表性采样。原文件、完整正文、图片二进制和向量不得进入请求。

### 6.2 LLM 调用

分类使用独立的非流式适配器，不复用聊天的流式输出行为。调用参数固定低温度，并要求返回符合 JSON Schema 的对象：

```json
{
  "top_category": "技术与工具",
  "subcategory": "AI 与检索",
  "create_subcategory": true,
  "tags": ["RAG", "混合检索", "评测"],
  "summary": "介绍混合检索与重排评测方法。",
  "confidence": 0.94
}
```

字段长度、标签数量和分类层级由服务端校验，不能直接信任模型输出。模型建议的顶层分类不在固定集合时映射到最接近的现有顶层分类或“其他”。

### 6.3 分类去重与自动创建

保存新的二级分类前依次执行：

1. 名称规范化，处理大小写、空白、全半角和常见后缀；
2. 当前父分类下精确名称与别名匹配；
3. 使用现有 Embedding 比较分类名称与说明，默认相似度达到 0.90 时复用已有分类；
4. 仍无匹配时创建新的二级分类。

分类去重阈值必须在分类基准集上校准。若阈值调整，更新 `classification_version` 并只重跑受影响文档。

自动合并只处理同一顶层分类下、均由 LLM 创建且语义相似度达到 0.95 的二级分类。系统保留创建时间较早的分类作为规范分类，将另一分类归档并迁移文档；包含用户创建分类、用户手动分类结果或跨顶层候选时禁止自动合并。合并在单个数据库事务内完成并写入完整反向事件。

### 6.4 幂等与重跑

幂等键由 `user_id + document_key + document_version + classification_version` 组成。相同键已有成功结果时不得再次调用 LLM。

自动重跑只在以下情况发生：

- 文档版本变化；
- 分类器或 Prompt 版本升级；
- 二级分类合并后存在受影响文档；
- 用户显式点击“重新编目”。

分类树变化不会触发全量重跑，只处理受影响分类和“其他”中的文档。

## 7. 故障处理

- 分类层最多进行两次应用级尝试；专用 LLM 客户端不再叠加隐藏重试，保证总调用次数可预测。
- 超时、限流、网络故障、拒绝响应和 JSON 校验失败统一转入 Embedding 兜底。
- 兜底只匹配已有分类；无法超过经基准集标定的置信阈值时归入“其他”。
- 编目失败不回滚已完成的解析、分块、向量索引和 BM25 索引。
- 前端显示聚合状态，不弹出要求用户处理的逐文档错误。
- 设置中关闭自动编目后，新文档保持 `classification_method=none`，仍可正常检索。
- LLM 恢复后，系统可在空闲时自动补跑 `failed` 文档；同一文档采用指数退避并设置每日调用上限，避免故障风暴。

## 8. 用户界面

视觉方案采用已确认的“A · 分类侧栏”。

### 8.1 主界面

- 左侧显示“全部文档”、七个顶层分类及可展开的二级分类，并显示文档计数。
- 中间显示文档列表、搜索框和分类/标签/文件类型/时间筛选。
- 文档行显示分类路径、自动标签、摘要和编目状态。
- 顶部只显示批量结果，例如“12 份文档已自动编目”；不制造人工待办。
- 分类首页方案中的总量和近期变化作为轻量概览组件，不替代主列表。
- 自动整理动态作为“整理记录”二级页面，展示可撤销的分类创建、合并和迁移。

### 8.2 与问答的关系

- 点击分类默认只筛选文档列表，不改变聊天检索范围。
- 聊天输入区提供“仅检索当前分类”开关，默认关闭。
- 开关开启时，请求显式携带 `category_id`，后端在租户过滤之后再添加分类过滤。
- 搜索和问答结果继续展示原文引用；分类不能替代来源证据。

### 8.3 可选人工操作

用户可以移动文档、编辑标签或重新编目，但这些操作不是完成自动分类的前置步骤。用户手动选择分类后，该分类结果标记为 `user`，后续自动重跑默认不覆盖，除非用户明确选择“允许重新编目覆盖”。

## 9. API 与模块边界

### 9.1 后端模块

- `classification_service`：分类包构造、脱敏、LLM 调用、Schema 校验和结果编排。
- `category_service`：分类树、名称规范化、去重、创建、归档、迁移和撤销。
- `classification_fallback`：基于现有 Embedding 的分类匹配。
- 文档处理服务只负责在解析与索引完成后投递编目任务。

### 9.2 API

- `GET /api/categories`：返回当前用户分类树与计数。
- `GET /api/categories/activity`：返回整理记录。
- `POST /api/categories/activity/{event_id}/revert`：撤销可逆操作。
- `POST /api/documents/{id}/reclassify`：可选的单文档重新编目。
- `GET /api/documents`：增加 `category_id`、`file_type`、`date_from`、`date_to` 筛选。
- `POST /api/chat`：增加可选 `category_id`，未提供时保持全库检索。
- 设置 API 增加自动编目开关、分类模型覆盖项和每日调用上限；API key 继续只从安全配置读取，不持久化到普通设置文件。

所有分类和文档接口先应用当前用户范围，再处理资源 ID，防止跨用户枚举。

撤销前必须检查相关分类和文档在目标事件之后是否又被修改；存在后续冲突时返回 HTTP 409，不覆盖较新的结果。用户可以改用“重新编目”让系统自动收敛，不要求手工逐份恢复。

## 10. 测试与验收

### 10.1 分类基准

为仓库现有 24 份受控语料补充人工顶层分类与合理二级分类。固定模型、Prompt 和温度后执行两轮：

- 顶层分类正确数不少于 22/24；
- 两轮顶层分类一致数不少于 23/24；
- 不出现第三层分类；
- 不出现跨顶层的同名重复二级分类；
- 自动标签数量始终为 3～8 个。

标签具有多解，不设置机械的逐字命中率；通过格式约束、人工抽查和同义归一化检查验收。

### 10.2 后端测试

- 分类包采样上限、敏感信息脱敏及禁止本地路径进入请求；
- 合法、缺字段、超长、未知顶层分类和非 JSON 模型响应；
- 两次尝试后切换 Embedding 兜底；
- LLM 与兜底均失败时文档仍保持可检索；
- 幂等键阻止重复调用与重复标签；
- 二级分类精确去重、语义去重、自动创建和最大层级约束；
- 用户隔离、跨用户资源 ID 拒绝和标签唯一约束；
- 分类迁移、撤销和手动分类保护；
- `category_id` 仅在显式传入时收窄检索。

外部 LLM、Embedding 和网络调用全部 Mock，保证测试确定性。

### 10.3 前端与端到端测试

- 分类树展开、计数、文档筛选和组合过滤；
- 自动编目聚合状态、兜底状态和整理记录；
- “仅检索当前分类”默认关闭并正确传参；
- 移动端抽屉中的分类导航可用；
- 端到端导入混合类型文档，等待解析完成和编目完成，验证筛选、摘要、标签和全库问答不受影响；
- LLM 故障场景下验证文档仍能搜索并显示兜底状态。

## 11. 数据迁移与回滚

- Alembic 迁移新增分类表、编目事件表、文档编目字段及必要索引。
- 为每个现有用户创建七个系统顶层分类。
- 现有文档初始设置为 `classification_status=pending`，由限速后台任务分批补编目，不阻塞启动。
- 调整标签唯一约束前先按用户范围检测重名并生成确定性迁移结果。
- 功能由 `auto_classification_enabled` 控制；关闭后停止新任务，现有分类数据保留且不影响检索。
- 数据库回滚只撤销新增表、字段和约束；不得删除原文、向量或现有用户手动标签。

## 12. 安全与可观测性

- 日志记录文档 ID、模型、耗时、状态、错误类别和 token 用量，不记录分类包正文、API key 或模型原始响应。
- 设置页明确提示自动编目会把脱敏代表片段发送到用户配置的 LLM 服务。
- 每日调用上限、超时和批量并发数可配置，默认采用保守值。
- 提供本地统计：成功率、兜底率、平均耗时、自动创建分类数和“其他”占比。
- “其他”占比持续升高只形成诊断提示，不转化为必须人工处理的任务。

## 13. 竞品借鉴边界

- 借鉴 RAGFlow 的分块可见性和检索测试，但第一版不要求用户人工干预每个分块。
- 借鉴 Open WebUI 的全库知识组织和检索范围切换，但保持 ChromaDB 嵌入式本地边界。
- 借鉴 Kotaemon 的引用与原文预览，分类只做导航，不替代证据展示。
- 不复制 Dify 的通用工作流平台，也不进入 Onyx 的企业连接器与权限同步范围。

## 14. 最终决策摘要

- 用户场景：个人、多领域、文档数量可持续增长。
- 内容组织：一个个人总库，固定顶层分类、自动二级分类、多标签。
- 分类引擎：现有 LLM 为主，现有 Embedding 为故障兜底，不新增本地大模型。
- 人工负担：零必需确认；所有人工调整均为可选。
- 界面：分类侧栏为主，分类统计为概览，整理动态为二级页面。
- 检索：默认跨全部分类，只有用户显式启用时按当前分类收窄。
- 安全：仅发送脱敏代表片段，不发送原文件、完整正文、本地路径或向量。
