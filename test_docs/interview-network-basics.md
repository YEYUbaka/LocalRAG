## 一、网络分层模型

### Q1: OSI七层模型和TCP/IP四层模型？⭐

**简答：**
> OSI七层：物理层→数据链路层→网络层→传输层→会话层→表示层→应用层
> TCP/IP四层：网络接口层→网络层→传输层→应用层

**详细回答：**

| OSI七层 | TCP/IP四层 | 功能 | 协议 |
|---------|-----------|------|------|
| 应用层 | 应用层 | 为用户应用提供服务 | HTTP, FTP, SMTP, DNS |
| 表示层 | 应用层 | 数据格式转换、加密 | SSL/TLS |
| 会话层 | 应用层 | 建立、管理会话 | RPC |
| 传输层 | 传输层 | 端到端通信 | TCP, UDP |
| 网络层 | 网络层 | 路由、寻址 | IP, ICMP, ARP |
| 数据链路层 | 网络接口层 | 帧传输、差错检测 | Ethernet |
| 物理层 | 网络接口层 | 比特流传输 | 双绞线、光纤 |

**面试口诀：**
> "物数网传会表应"（从下到上）

---

### Q2: TCP和UDP的区别？⭐⭐

**简答：**
> TCP面向连接、可靠传输、有序、一对一；UDP无连接、不可靠、无序、支持一对多。

**详细回答：**

| 维度 | TCP | UDP |
|------|-----|-----|
| 连接 | 面向连接（三次握手） | 无连接 |
| 可靠性 | 可靠（确认、重传、流控） | 不可靠 |
| 有序性 | 有序（序号+确认号） | 无序 |
| 传输方式 | 面向字节流 | 面向报文 |
| 通信方式 | 一对一 | 一对一、一对多、多对多 |
| 速度 | 较慢 | 较快 |
| 头部开销 | 20字节 | 8字节 |
| 应用场景 | 文件传输、网页、邮件 | 视频、语音、游戏、DNS |

**面试口诀：**
> "TCP可靠慢，UDP快但不可靠"

## 二、TCP协议

### Q3: TCP三次握手过程？⭐⭐

**简答：**
> SYN → SYN+ACK → ACK，客户端和服务器同步序列号并确认连接。

**详细回答：**

```
客户端                    服务器
  |                        |
  |------- SYN(seq=x) ---->|  第1次握手：客户端发送SYN
  |                        |
  |<-- SYN+ACK(seq=y,      |  第2次握手：服务器回复SYN+ACK
  |     ack=x+1) ----------|
  |                        |
  |------- ACK(ack=y+1) -->|  第3次握手：客户端确认ACK
  |                        |
  连接建立                  连接建立
```

**为什么是三次而不是两次？**
> 防止已失效的连接请求到达服务器。如果只有两次，客户端发的第一个SYN在网络中延迟，客户端超时重发后建立了连接。但第一个SYN后来到达服务器，服务器以为是新连接，发送确认后白白等待，浪费资源。

**追问：三次握手中可以携带数据吗？**
> 第1、2次不能携带数据，第3次可以。因为第1、2次时连接还未建立，携带数据可能被攻击者利用。

---

### Q4: TCP四次挥手过程？⭐⭐

**简答：**
> FIN → ACK → FIN → ACK，双方各自关闭发送通道。

**详细回答：**

```
客户端                    服务器
  |                        |
  |------- FIN(seq=u) ---->|  第1次：客户端请求关闭
  |                        |
  |<------ ACK(ack=u+1) ---|  第2次：服务器确认收到
  |                        |  （服务器可能还有数据要发）
  |<------ FIN(seq=w) -----|  第3次：服务器也请求关闭
  |                        |
  |------- ACK(ack=w+1) -->|  第4次：客户端确认
  |                        |
  等待2MSL后关闭            关闭
```

**为什么是四次而不是三次？**
> TCP是全双工通信，每个方向需要单独关闭。服务器收到FIN时可能还有数据没发完，所以先回复ACK确认收到，等数据发完再发FIN。

**为什么客户端要等待2MSL（最大报文段生存时间）？**
> 1. 确保服务器收到最后的ACK（如果ACK丢失，服务器会重发FIN）
> 2. 让本次连接的所有报文在网络中消失，避免影响新连接

---

### Q5: TCP如何保证可靠传输？⭐⭐

**简答：**
> 序号、确认重传、流量控制、拥塞控制、校验和。

**详细回答：**

**1. 序号与确认号**
- 每个字节都有序号
- 接收方收到数据后发送ACK确认

**2. 超时重传**
- 发送数据后启动定时器
- 超时未收到ACK则重传

**3. 流量控制（滑动窗口）**
- 接收方告诉发送方自己的接收窗口大小
- 发送方根据窗口大小控制发送速率

**4. 拥塞控制**
- 慢启动：指数增长
- 拥塞避免：线性增长
- 快重传：收到3个重复ACK立即重传
- 快恢复：窗口减半而非从0开始

**5. 校验和**
- 检测数据在传输中是否出错

## 三、HTTP协议

### Q6: HTTP和HTTPS的区别？⭐⭐

**简答：**
> HTTP明文传输不安全，HTTPS = HTTP + SSL/TLS加密，端口80 vs 443。

**详细回答：**

| 维度 | HTTP | HTTPS |
|------|------|-------|
| 安全性 | 明文传输 | 加密传输 |
| 端口 | 80 | 443 |
| 证书 | 不需要 | 需要CA证书 |
| 性能 | 较快 | 略慢（加解密开销） |
| 连接方式 | 简单 | SSL握手 |

**HTTPS工作原理：**
1. 客户端发起HTTPS请求
2. 服务器返回证书（含公钥）
3. 客户端验证证书，生成随机密钥
4. 用公钥加密随机密钥发给服务器
5. 服务器用私钥解密得到随机密钥
6. 双方用随机密钥进行对称加密通信

**追问：为什么不全程用非对称加密？**
> 非对称加密计算量大，速度慢。所以只在握手阶段用非对称加密交换密钥，之后用对称加密通信。

### Q7: HTTP常见状态码？⭐

**简答：**
> 200成功、301永久重定向、302临时重定向、304未修改、400请求错误、401未授权、403禁止、404未找到、500服务器错误、502网关错误、503服务不可用

**详细回答：**

| 状态码 | 含义 | 典型场景 |
|--------|------|----------|
| 200 | OK | 请求成功 |
| 201 | Created | 资源创建成功（POST） |
| 204 | No Content | 删除成功 |
| 301 | 永久重定向 | 网站换域名 |
| 302 | 临时重定向 | 临时跳转 |
| 304 | Not Modified | 缓存有效 |
| 400 | Bad Request | 参数错误 |
| 401 | Unauthorized | 未登录 |
| 403 | Forbidden | 无权限 |
| 404 | Not Found | 资源不存在 |
| 405 | Method Not Allowed | 请求方法不允许 |
| 500 | Internal Server Error | 服务器内部错误 |
| 502 | Bad Gateway | 网关错误 |
| 503 | Service Unavailable | 服务不可用 |

### Q8: Cookie、Session和Token的区别？⭐⭐

**简答：**
> Cookie存在客户端，Session存在服务器端，Token是无状态的认证凭证。

**详细回答：**

| 维度 | Cookie | Session | Token |
|------|--------|---------|-------|
| 存储位置 | 客户端浏览器 | 服务器 | 客户端 |
| 安全性 | 较低 | 较高 | 较高 |
| 服务器压力 | 小 | 大（需存储） | 小（无状态） |
| 跨域支持 | 受限 | 受限 | 支持 |
| 典型应用 | 记住密码、跟踪 | 用户登录状态 | JWT认证 |

**追问：什么是JWT？**
> JWT（JSON Web Token）是一种基于JSON的开放标准，用于在各方之间安全地传输信息。由三部分组成：
> - Header（头部）：算法和类型
> - Payload（载荷）：用户信息
> - Signature（签名）：验证Token完整性

---

### Q9: HTTP的无状态协议是什么意思？怎么解决？⭐⭐

**简答：**
> 无状态指服务器不记住每次请求的关系。通过Cookie、Session、Token解决。

**详细回答：**
HTTP无状态意味着：每个请求都是独立的，服务器不知道客户端之前的状态。

**解决方案：**
1. **Cookie**：服务器在响应中设置Cookie，浏览器下次请求时自动携带
2. **Session**：服务器保存会话信息，客户端只保存SessionID
3. **Token**：客户端保存Token，每次请求携带，服务器验证即可

## 四、DNS解析

### Q10: DNS解析过程？⭐⭐

**简答：**
> 域名 → 本地DNS缓存 → 本地DNS服务器 → 根DNS → 顶级DNS → 权威DNS → IP地址

**详细回答：**

```
1. 浏览器缓存 → 检查是否有该域名的缓存
2. 操作系统缓存 → 检查hosts文件和系统DNS缓存
3. 本地DNS服务器 → 向配置的DNS服务器查询
4. 根DNS服务器 → 返回顶级域DNS地址（如.com）
5. 顶级DNS服务器 → 返回权威DNS地址
6. 权威DNS服务器 → 返回最终IP地址
7. 本地DNS服务器 → 缓存结果并返回给客户端
```

**追问：什么是DNS劫持？**
> DNS劫持是指攻击者篡改DNS解析结果，将域名指向错误的IP地址。常见表现：
> - 访问正常网站跳转到广告页面
> - 网络正常但某些网站打不开

## 五、网络安全

### Q11: 什么是ARP协议？⭐⭐

**简答：**
> ARP（地址解析协议）将IP地址解析为MAC地址。

**详细回答：**
- **工作原理**：主机A要发送数据给主机B，知道B的IP但不知道MAC地址
- **ARP请求**：主机A广播ARP请求，询问"谁的IP是xxx？"
- **ARP响应**：主机B回复自己的MAC地址
- **ARP缓存**：主机A将IP-MAC映射保存在缓存中

**追问：什么是ARP欺骗？**
> 攻击者发送伪造的ARP响应，将自己的MAC地址与目标IP绑定，从而截获数据。

---

### Q12: 什么是跨域？怎么解决？⭐⭐

**简答：**
> 跨域是浏览器同源策略限制，不同协议/域名/端口的请求被阻止。通过CORS、JSONP、代理解决。

**详细回答：**

**同源策略：**
协议、域名、端口都相同才是同源。

**解决方案：**
1. **CORS**（推荐）：服务器设置Access-Control-Allow-Origin头
2. **JSONP**：利用script标签不受同源策略限制
3. **代理服务器**：后端转发请求
4. **Nginx反向代理**：配置跨域头
